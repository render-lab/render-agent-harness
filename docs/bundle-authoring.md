# Authoring a bundle template

A **bundle** is a sealed multi-agent gallery template — one harness deployment hosts several agents that share Postgres, Key Value, one web service, one worker, and N cron services (one per cron schedule). The first bundle is `chief-of-staff`. This doc covers how to add another.

The design rationale lives in [`bundles-plan.md`](./bundles-plan.md); the gallery loader + cross-check lives in [`gallery-plan.md`](./gallery-plan.md).

## 1. When to ship a bundle (vs. an agent)

Use a **bundle** when the template's value comes from multiple agents working together:

- "Chief of Staff" — chat + meeting-prep cron + weekly-recap cron, sharing memory.
- "Interviewer" *(future)* — structured Q&A web + scoring worker + report-write cron.
- "Site Watcher" *(future)* — scrape cron + diff worker + alert webhook.

Use a single **agent** template when one agent on one runtime is the full story (e.g. `chat`, `research-cron`).

## 2. Files to add

```
gallery/agents/<bundle-slug>/
├── README.md
├── render-harness.yaml             # V2, schemaVersion: 2, agents: [...]
└── src/
    ├── <agent-id>.ts               # one per bundled agent
    └── ...
```

That's it. The gallery loader (`packages/registry/src/gallery.ts:collectBundleSources`) walks `src/` and embeds every file in the bundled-gallery snapshot. The scaffolder copies them through verbatim and generates `src/web.ts` / `src/worker.ts` / `src/cron.ts` on top.

## 3. Writing `render-harness.yaml` (V2)

```yaml
schemaVersion: 2
name: <bundle-slug>
description: One-line pitch.
harnessVersion: "^0.2"
license: MIT

# Bundle-wide defaults. Per-agent overrides allowed for model / permissions / etc.
shared:
  model:
    provider: anthropic
    model: claude-sonnet-4-6
  ui: true                          # mount @render-harness/ui on the web service

# Bundle-wide cap packs. Packs are module singletons — each pack instance is
# shared across every agent in the bundle; per-agent `capabilities` is not
# modeled. All bundled agents see the same memory namespace, etc.
capabilities:
  - pack: "@render-harness/cap-memory-pg"

# Flat env schema. Convention is to namespace by agent id when ambiguous
# (e.g. MEETING_PREP_CALENDAR_URL); the emitter propagates every env var
# to every service.
envSchema:
  - name: SOME_API_KEY
    required: true
    secret: true

agents:
  - id: chat                        # slug; unique within the bundle
    description: ...                # surfaces in the bundle review screen
    agent:
      kind: custom
      entrypoint: ./src/chat.ts
    runtimes:
      - kind: web
      - kind: worker
  - id: nightly
    agent:
      kind: custom
      entrypoint: ./src/nightly.ts
    runtimes:
      - kind: cron
        schedule: "0 2 * * *"
```

Rules the schema enforces:

- `agents[].id` must be a slug, unique within the bundle.
- Each agent must have at most one runtime of each kind (a single agent can't be `kind: web` twice). Cross-agent duplication is fine — the emitter coalesces web/worker into one service each and fans cron out to N services.
- Every agent must have a model. Per-agent `model:` overrides `shared.model:`; omitting both is an error.

## 4. Writing each `src/<agent-id>.ts`

Default-export a function that returns an `AgentDefinition` (or export the definition directly). The scaffolder copies these verbatim — the user customizes them after scaffolding.

```ts
import { type AgentDefinition, defineAgent } from "@render-harness/core";

export default function buildAgent(): AgentDefinition {
  return defineAgent({
    name: "<agent-id>",            // match the manifest id; the registry rewrites this anyway
    version: "0.1.0",
    model: { provider: "anthropic", model: "claude-sonnet-4-6" },
    systemPrompt: SYSTEM_PROMPT,
  });
}

const SYSTEM_PROMPT = `\
...
`;
```

Notes:

- `defineAgent({ name })` is overridden to the bundle entry's `id` at load time — so the name in the file is informational. The runtime registry routes by `id`.
- Capability tools (e.g. `memory.write`, `memory.search`) come in *namespaced*: `render-harness/cap-memory-pg__memory.search`. Reference these names in your system prompt so the model knows what's available.
- The bundle's three runtime entrypoints — generated by the scaffolder, not by you — handle the runtime wiring:
  - `src/web.ts` calls `serveWeb({ agents: agentsById })`
  - `src/worker.ts` calls `startWorkerAndWait({ agent: (job) => agentsById[job.agentName] })`
  - `src/cron.ts` calls `runCronFromRegistryAndExit({ agents: agentsById, agentId: process.env.HARNESS_AGENT_ID! })`

## 5. Register in `gallery/index.yaml`

```yaml
  - slug: <bundle-slug>
    name: "Display Name"
    description: "Short pitch shown on the Template step."
    path: ./agents/<bundle-slug>
    categories: ["bundle", "..."]
    runtimeKinds: ["web", "worker", "cron"]      # union across all agents
    capabilities:
      - "@render-harness/cap-memory-pg"
    author: "render-harness"
```

The loader cross-checks that `runtimeKinds` matches the union of every agent's runtimes (`flattenRuntimeKinds(manifest)`). The discriminator (`kind: "bundle"`) is *derived* from the manifest at load time — you do not declare it in `index.yaml`.

## 6. Re-bundle the gallery snapshot

The CLI ships with a frozen snapshot at `packages/create-render-agent/bundled-gallery/gallery.json`. After adding a bundle:

```sh
cd packages/create-render-agent
pnpm tsx scripts/bundle-gallery.ts
```

Then verify:

```sh
pnpm --filter "@render-harness/registry" test            # cross-check + parse
pnpm --filter "create-render-agent" test                 # buildFileMap snapshots
```

The bundle e2e test (`packages/create-render-agent/src/bundle-e2e.test.ts`) loads the real gallery and exercises the full file map for `chief-of-staff`. Mirror it for your bundle to catch regressions early.

## 7. What the emitter does with a bundle

Given a 3-agent bundle (chat web+worker, two cron agents):

| Render service | Reason |
|---|---|
| 1 Postgres | All agents share `agent_runs` etc. |
| 1 Key Value | Cancellation flags + cap-memory-pg cache. |
| 1 web | `serveWeb({ agents: agentsById })` — multi-tenant, routes by `agentName`. |
| 1 worker pserv | `startWorker({ agent: (job) => agentsById[job.agentName] })` — multi-tenant resolver. |
| N crons | One Render Cron per cron-runtime entry across all agents. Named `<bundle>-cron-<agentId>`. Env var `HARNESS_AGENT_ID=<id>` selects the agent at boot. |

Single-agent V1 manifests still emit V1-style names (`<name>`, `<name>-web`, `<name>-worker`) so existing gallery entries don't churn.

## 8. Scheduled work: cron, workflows, or both

Bundles support three modes for scheduled / on-demand agent work. See [`cron-workflows-plan.md`](./cron-workflows-plan.md) for the design rationale. The choice is per-runtime, declared in the manifest.

| Mode | Manifest | Use when |
|---|---|---|
| **Cron, inline** | `kind: cron`, default (`via: cron`) | Short fail-stop work. No HITL. Cheap to run. e.g. "check the calendar every 15 minutes". |
| **Cron, triggers workflow** | `kind: cron`, `via: workflow` (implies `workflowTask: true`) | Long-running, durable, or HITL-capable scheduled work. The Cron service is a thin trigger; the actual run executes in the bundle's Workflow service. e.g. "weekly recap", "deep research dive every morning". |
| **Workflow-only, agent-triggered** | `workflowTask: true` (no schedule) | On-demand durable work. Another agent invokes it via the `trigger_workflow` builtin. e.g. chat agent delegates "do a deep dive on X". |

Picking guidance:

- **Default to inline cron.** Most periodic checks fit (30s of work, fail-stop, no approval gate). Each is ~$0.50/mo on starter.
- **Move to `via: workflow` when** the work runs longer than a few minutes, multi-step with checkpoints, or you want HITL approval before destructive actions land. Render Workflows give you a durable execution graph, automatic retries, and per-step observability.
- **Use `workflowTask: true` without a schedule when** the agent should be callable on demand (by chat, by another workflow, by a webhook from your CI) but not on a fixed cadence.

### What `via: workflow` actually deploys

For a `kind: cron, via: workflow` runtime, the emitter produces:

- A small Render Cron service named `<bundle>-cron-trigger-<agentId>`. Its start command is `node dist/cron-trigger.js`. The service runs for ~100ms per invocation: import the Render SDK, call `runTask`, exit. No model inference.
- A registered task on the bundle's single Workflow service (slug: `<bundle>-workflows`). The Workflow service hosts every `workflowTask: true` agent in the bundle as one task each — Render supports up to 500 tasks per service.

The Workflow service is **not Blueprintable today**. The emitter prints a single consolidated Dashboard checklist line:

> Create one Render Workflow service named `<bundle>-workflows`, link this repo, set the build command to `… pnpm --filter <package> build` and the start command to `node examples/<bundle>/dist/workflows.js`. It will host these tasks: `task-a`, `task-b`, …

A future `render-harness workflows sync` CLI will automate this via the Render API; until then, the Dashboard step is one click per bundle.

### `RENDER_API_KEY` distribution

When the bundle has any workflow-task agent, the emitter wires two env vars onto web, worker, and every cron-trigger service:

- `WORKFLOW_SLUG=<bundle>-workflows` (value, not secret) — read by the `trigger_workflow` builtin to compose task refs.
- `RENDER_API_KEY` (sync: false) — the user provides at deploy time.

Bundles with no workflow-task agents don't get these env vars (no point shipping a secret slot the user has to fill in for nothing).

### Extensibility: agents authoring new agents

Because the Workflow service auto-registers every `task()` call on boot, the architecture supports agents writing new agents:

1. A chat agent (with filesystem + git capability packs) writes a new `src/<new-agent>.ts` to the bundle repo.
2. Commits + pushes to the linked GitHub repo.
3. Render auto-rebuilds the Workflow service (~30s).
4. The new task is registered on next boot, immediately callable via `trigger_workflow({ agent: "<new-agent>" })`.

No infrastructure changes needed. Same pattern works for adding `via: workflow` cron entries — the bundle's Render services redeploy from the linked repo on push.

### `trigger_workflow` builtin

When `RENDER_API_KEY` + `WORKFLOW_SLUG` are present, every agent in the bundle gets a Tier-B builtin tool:

```jsonc
trigger_workflow({
  agent: "weekly-recap",       // an agent in this bundle with workflowTask: true
  input: "deep recap of Q3",   // optional initial content for the new run
  await: false                  // fire-and-forget; default
})
// returns: { taskRef, runId, taskRunId, status?, results? }
```

Gate it with `permissions.requireApproval: ["trigger_workflow"]` to force a HITL pause before any agent-initiated workflow run actually launches.
