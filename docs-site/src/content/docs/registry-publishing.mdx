---
title: Registry Publishing
description: Publish a pinned deployable repo so others can deploy it from the registry.
---

Use the registry publishing flow when you have a working loop in its own Git repository and want other people to discover and deploy that exact loop from `/browse`.

Registry publishing is not the starter-template workflow. If you are adding a scaffoldable starter to this repository, use [Template catalog](/template-catalog/) instead. If that starter is a multi-agent bundle, use [Authoring bundle templates](/authoring-bundle-templates/) as the bundle-specific subcase.

The public wizard site’s `/browse` route shows community registry entries alongside official templates. Community entries point at external, immutable deployable repos. Each entry is pinned to a Git commit SHA so the generated Render Blueprint and source code are reproducible.

## Publishing flow

1. Scaffold or create a working project in its own Git repo.
2. Add `render-harness.yaml`, custom agent code, MCP servers, capabilities, and environment schema.
3. Generate `render.yaml` from the manifest.
4. Commit the manifest, generated Blueprint, source files, and README.
5. Pin the registry entry to a Git commit SHA.
6. Submit the entry to the community registry index.

## Generate the Blueprint

Run the Blueprint build before publishing:

```sh
pnpm build:bp
```

The build reads `render-harness.yaml`, validates the manifest, resolves capability packs, writes `render.yaml`, and prints the environment variables that the deploy will ask users to provide.

Use the drift check in CI:

```sh
pnpm build:check
```

`build:check` exits nonzero when `render.yaml` is stale relative to `render-harness.yaml`.

## Commit and pin

Commit the generated files, then capture the SHA:

```sh
git rev-parse HEAD
```

Registry entries should point at an immutable SHA, not a floating branch. This makes Deploy to Render links reproducible.

## Submit to the registry

Use `/browse` on the public wizard site to find published entries.

Official templates and community submissions appear together, but they have different source data. Official templates come from `gallery/`. Community submissions come from `registry-index/index.json`.

The registry records entries with this shape:

```json
{
  "name": "my-agent",
  "description": "One-line description.",
  "repo": "https://github.com/<owner>/my-agent",
  "ref": "<40-character-sha>",
  "categories": ["chat", "demo"]
}
```

Index CI validates the index shape, fetches `render-harness.yaml` at the pinned SHA, and validates the manifest.

## README badge

Published entries should include a Deploy to Render badge near the top of the README. `render-harness-build` prints a badge snippet after generating the Blueprint.

## Environment interpolation

MCP server fields and capability config can reference environment variables:

```yaml
mcpServers:
  - name: render
    transport: http
    url: https://mcp.render.com/mcp
    headers:
      Authorization: "Bearer ${RENDER_API_KEY}"
      X-Optional: "${MAYBE:-default-value}"
```

Interpolation rules:

- `${VAR}` is required and throws if unset.
- `${VAR:-fallback}` uses `fallback` when unset.
- `\${VAR}` stays literal.

Declare user-provided values in `envSchema` so the Blueprint, scaffolder, and operator surfaces can explain them.
