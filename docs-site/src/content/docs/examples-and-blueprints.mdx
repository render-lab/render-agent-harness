The repo includes examples and Blueprint files that exercise different deployment shapes. Use them to understand a runtime path before creating your own agent.

Examples are reference implementations, not product boundaries. Some are useful as-is for demos or internal tools; most are meant to be adapted. Swap prompts, replace capabilities, add MCP servers, change runtime paths, or split one example into several agents when your workflow needs it.

## Root commands

Run these from the repo root:

```sh
pnpm db:up
pnpm dev:web
pnpm dev:citations
pnpm dev:operator-web
pnpm dev:operator-worker
```

Docker Compose profiles provide app stacks for selected examples:

```sh
pnpm apps:web-chat
pnpm apps:support
pnpm apps:operator-demo
pnpm apps:citations
```

## Examples

| Example | Purpose | Runtime shape |
| --- | --- | --- |
| `examples/web-chat` | Minimal web chat example. | Sync web |
| `examples/support-agent` | Web plus worker support flow. | Web + worker |
| `examples/operator-demo` | Operator UI and worker demo. | Web + worker + UI |
| `examples/citations-monitor` | Scheduled citation monitoring. | Cron |
| `examples/deploy-agent` | Deployment/workflow-oriented agent. | Workflow-oriented |

`examples/deploy-agent` uses Render Workflows for durable, approval-friendly work. Create the Workflow service in the Dashboard, then run the example trigger command from its README to start or resume work.

## Gallery agents as examples

Gallery agents are also examples:

| Template | What it demonstrates |
| --- | --- |
| `gallery/agents/chat` | Minimal built-in chat agent manifest. |
| `gallery/agents/support-bot` | Queue-driven support starter. |
| `gallery/agents/research-cron` | Scheduled research and search capability. |
| `gallery/agents/chief-of-staff` | Multi-agent bundle with memory, Cron, Workflows, and chat. |

Use the gallery when you want a starter. Use `examples/` when you want a runnable local app.

If you are deciding whether to create a new template or a new example, use this rule: templates help authors start new projects, while examples help contributors and operators understand how a runtime path behaves.

## Blueprint files

The `blueprints/` directory contains reference Render Blueprints for hand-authored deployment shapes.

| File | Purpose |
| --- | --- |
| `blueprints/render.demo.yaml` | Simple demo web shape. |
| `blueprints/render.demo-cron.yaml` | Cron-oriented demo shape. |
| `blueprints/render.private.yaml` | Production-style web plus worker/private service shape. |
| `blueprints/render.hardened.yaml` | Hardened private-network shape with tighter deployment defaults. |

Generated projects usually get a `render.yaml` from the registry emitter rather than copying these files directly.

## Docker Compose

`compose.yaml` provides local Postgres and Key Value primitives. It also includes profiles for example app stacks.

Most tests and integration paths expect these primitives:

- Postgres on `127.0.0.1:55432`
- Key Value on `127.0.0.1:56379`

Use `HARNESS_PG_PORT` and `HARNESS_KV_PORT` if those ports are taken.
