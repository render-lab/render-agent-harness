Capabilities are package-level extensions that the registry merges into agent definitions. They keep integrations outside the core loop while still giving agents typed tools and deployment requirements.

The first-party packs are examples of the extension model, not a closed catalog. Add a capability pack whenever an integration should be reusable across agents or templates: a SaaS API wrapper, an MCP server configuration, a memory backend, an inbound connector, or extra Render services that should travel with an agent.

## What a capability can contribute

A capability pack can add:

- Local TypeScript tools (`localTools`).
- MCP server definitions (`mcpServers`).
- Skills loadable via `load_skill` (`skills`).
- Environment variable requirements (`envSchema`).
- Inbound webhook receivers mounted at `/connectors/<key>` (`connectors`).
- Extra Render services merged into the generated Blueprint (`renderServices`).

Capability packs are declared at the bundle level, not per agent. This avoids duplicating module-level setup inside a single Node process and lets a pack hold cross-agent state safely.

To publish your own pack, see [Authoring capability packs](/authoring-capability-packs/) for the full walkthrough.

## Declaring a capability

Capabilities are declared in your bundle's `render-harness.yaml` at the repo root:

```yaml title="render-harness.yaml"
capabilities:
  - pack: "@render-harness/cap-memory-pg"
  - pack: "@render-harness/cap-search-exa"
    config:
      maxResults: 5
```

The `config` object is pack-specific. Keep configuration small and move secret values into `envSchema`.

You also need the packs in your dependencies. Add them with pnpm/npm so they exist in `node_modules` at build and runtime:

```sh
pnpm add @render-harness/cap-memory-pg @render-harness/cap-search-exa
```

## Tool names

Capability tools are namespaced when they reach the model. The scope is stripped from the pack name and any `.` in the tool name becomes `_`:

| Pack | Tool | Namespaced name |
| --- | --- | --- |
| `@render-harness/cap-memory-pg` | `memory.write` | `cap-memory-pg__memory_write` |
| `@render-harness/cap-github` | `github.get_issue` | `cap-github__github_get_issue` |
| `@render-harness/cap-slack` | `slack.send_message` | `cap-slack__slack_send_message` |

Use the namespaced form in `permissions.allowedTools`, `permissions.deniedTools`, and `permissions.requireApproval` inside `render-harness.yaml`:

```yaml title="render-harness.yaml"
agents:
  - id: chat
    # ...
    permissions:
      requireApproval:
        - cap-memory-pg__memory_write
        - cap-slack__slack_send_message
```

Use `requireApproval` for tools that write durable state, trigger external work, or perform actions the user should review.

## Connector capabilities

Connector packs mount inbound webhooks on the web service and enqueue work for a worker runtime. For example:

| Pack | Webhook path | Notes |
| --- | --- | --- |
| `@render-harness/cap-github` | `/connectors/github` | One run per GitHub delivery. |
| `@render-harness/cap-linear` | `/connectors/linear` | One run per Linear webhook event. |
| `@render-harness/cap-slack` | `/connectors/slack` | One conversation per Slack thread. |
| `@render-harness/cap-webhook-generic` | `/connectors/webhook-generic` | HMAC-verified custom event sources. |

Provider packs default to `accessMode: read`. Set `accessMode: read_write` only when the agent should get mutation tools, such as posting a Slack reply or updating an issue.

Connector keys must match `[a-z0-9][a-z0-9-]*` and cannot collide with reserved web routes (`runs`, `agents`, `ui`, `usage`, etc.). For the connector contract and a working webhook handler example, see [Authoring capability packs › connectors](/authoring-capability-packs/#connectors).

## Installing after deployment

Already-deployed harnesses install capabilities through the Operator UI. The UI commits source changes through the wizard service and GitHub App instead of editing the running process directly.

The first install flow commits:

- `render-harness.yaml` capability config and permissions.
- `package.json` dependency changes.
- `.env.example` placeholders for required secrets when present.

After the commit merges and Render redeploys, set the required secrets in the Config tab. Lockfile and `render.yaml` refresh are still follow-up steps: run `pnpm install` and `pnpm build:bp` in source control to commit those generated changes.
