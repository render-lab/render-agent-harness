---
title: Authoring Capability Packs
description: Ship reusable tools, MCP servers, skills, connectors, and Render service requirements for agents.
---

A capability pack is an npm package that extends agents without adding behavior to the core loop. Reach for a pack whenever an integration should be reusable across agents, bundles, or templates: a SaaS API wrapper, a hosted MCP server, an inbound webhook receiver, a memory backend, or extra Render services that should travel with the deployment.

This guide is the full author walkthrough. For the reference summary of what packs are and how users declare them, see [Capabilities](/capabilities/).

## What a pack can contribute

Every contribution is optional. A pack declares one or more of:

| Contribution | When called | Purpose |
| --- | --- | --- |
| `envSchema` | Build and deploy | Env vars the pack needs. Merged into the bundle's effective schema, surfaced to deploy-time UI. |
| `localTools` | Runtime | TypeScript tool handlers passed to the model. Namespaced as `<pack>__<tool>`. |
| `mcpServers` | Runtime | MCP server definitions started or connected at agent boot. |
| `skills` | Runtime | Skill metadata surfaced in the system prompt and loadable via `load_skill`. |
| `connectors` | Runtime | Inbound HTTP receivers mounted on the web service at `/connectors/<key>`. |
| `renderServices` | Build only | Extra Render services merged into the generated `render.yaml`, e.g. a sidecar pserv. |

Capability packs are declared at the bundle level, not per agent, because each pack is loaded once per Node process and may hold module-level state. Users do not redeclare a pack's `envSchema` in their own `render-harness.yaml`.

## Files you will touch

Inside the pack you author:

| File | Required | Purpose |
| --- | --- | --- |
| `package.json` | yes | Package metadata. Must declare ESM, the `render-harness-cap` keyword, and the right `exports`. |
| `tsconfig.json` | yes | TypeScript compiler settings. |
| `tsup.config.ts` | yes | Build settings. Emits `dist/index.js` + `dist/index.d.ts`. |
| `src/index.ts` | yes | Default-exports the `CapabilityPack`. |
| `src/*.ts` | optional | Split out tools, signature verification, helpers. |
| `src/*.test.ts` | optional | Vitest tests. |
| `vitest.config.ts` | optional | Test runner config. |
| `skills/*.md` | optional | Skill bodies, if the pack contributes skills. |
| `README.md` | recommended | Document config keys, namespaced tool names, env vars, and side effects. |

Inside the user's harness repo (only relevant when listing an official pack or when documenting how users adopt yours):

| File | Purpose |
| --- | --- |
| `render-harness.yaml` | User declares `capabilities: - pack: ...` and any `permissions:`. |
| `package.json` | User adds your pack as a dependency. |
| `capability-catalog/index.yaml` | Maintained in this repo; only edited when adding/updating an official catalog listing. |

## Package layout

A capability pack is a standalone npm package. Create it as a new repo, or as a workspace package alongside your other code. Every file below is created by you — the harness does not scaffold capability packs.

```text
my-pack/
  src/
    index.ts            # default-exports the CapabilityPack (required)
  skills/               # optional, only if the pack ships skills
    example.md
  package.json          # required
  tsconfig.json         # required
  tsup.config.ts        # required (or your own build setup)
  README.md             # strongly recommended
  vitest.config.ts      # optional, for tests
  src/index.test.ts     # optional, for tests
```

`src/index.ts` is the entrypoint. The `dist/` directory is generated by `tsup build` and committed to npm but not to Git. The `skills/` folder, if used, is bundled into the published tarball and referenced from `skills()` via `import.meta.url`.

## package.json

The validator (`render-harness-capability validate`) enforces a specific shape. The following is a complete example. Copy it into `package.json` at the package root and adjust the name, description, and dependency versions.

```json title="package.json"
{
  "name": "@acme/render-harness-cap-example",
  "version": "0.1.0",
  "description": "Example capability pack for the Render agent harness.",
  "type": "module",
  "license": "MIT",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./package.json": "./package.json"
  },
  "files": ["dist", "skills"],
  "keywords": ["render-harness-cap", "render-harness"],
  "renderHarness": {
    "gallery": {
      "label": "Example",
      "envHint": "EXAMPLE_API_KEY"
    }
  },
  "scripts": {
    "build": "tsup",
    "typecheck": "tsc --noEmit",
    "test": "vitest run --passWithNoTests"
  },
  "dependencies": {
    "@render-harness/registry": "^0.2",
    "@render-harness/core": "^0.2"
  },
  "devDependencies": {
    "tsup": "^8.5.1",
    "typescript": "^6.0.3",
    "vitest": "^4.1.5",
    "@types/node": "^25.6.2"
  },
  "publishConfig": { "access": "public" },
  "repository": {
    "type": "git",
    "url": "git+https://github.com/<owner>/<repo>.git",
    "directory": "packages/cap-example"
  }
}
```

Validator rules to be aware of:

- `"type": "module"` is required. Packs are ESM only.
- `keywords` must contain `render-harness-cap`. Discovery tooling filters on this keyword.
- `exports["./package.json"]` is required so `@render-harness/registry` can read the installed version at runtime to compute compatibility diagnostics.
- `exports["."]` must expose an ESM entry. The validator falls back to `module` or `main`, but `exports` is preferred.
- `repository.url` should point at the canonical Git repo. npm Trusted Publishing requires it for provenance attestations.
- `renderHarness.gallery.label` (and optional `envHint`) is recommended metadata; it shows up in the operator UI's capability gallery.

## TypeScript and build tooling

Use `tsup` to emit ESM with type declarations. Create `tsup.config.ts` at the package root:

```ts title="tsup.config.ts"
import { defineConfig } from "tsup";

export default defineConfig({
  entry: { index: "src/index.ts" },
  format: ["esm"],
  dts: true,
  clean: true,
  sourcemap: true,
  target: "node22",
  splitting: false,
  treeshake: true,
});
```

Create `tsconfig.json` at the package root:

```json title="tsconfig.json"
{
  "extends": "@tsconfig/node22/tsconfig.json",
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "verbatimModuleSyntax": true,
    "exactOptionalPropertyTypes": true,
    "rootDir": "./src",
    "outDir": "./dist"
  },
  "include": ["src/**/*.ts"],
  "exclude": ["node_modules", "dist", "**/*.test.ts"]
}
```

Imports in `src/**/*.ts` must use the `.js` extension even when the source is `.ts`, and type-only imports must use `import type`.

## definePack

The default export of `src/index.ts` is the result of `definePack`. Start from this skeleton and remove the callbacks your pack does not need:

```ts title="src/index.ts"
import {
  definePack,
  type PackContext,
  type ConnectorContribution,
  type RenderServiceSpec,
} from "@render-harness/registry";
import type {
  LocalToolHandler,
  McpServerConfig,
  SkillMetadata,
} from "@render-harness/core";
import pkg from "../package.json" with { type: "json" };

const pack = definePack({
  name: "cap-example",
  version: pkg.version,
  envSchema: [],
  localTools(ctx: PackContext): LocalToolHandler[] {
    return [];
  },
  mcpServers(ctx: PackContext): McpServerConfig[] {
    return [];
  },
  skills(ctx: PackContext): SkillMetadata[] {
    return [];
  },
  connectors(ctx: PackContext): ConnectorContribution[] {
    return [];
  },
  renderServices(ctx: PackContext): RenderServiceSpec[] {
    return [];
  },
});

export default pack;
```

Constraints `definePack` enforces:

- `name` must match `[a-z0-9][a-z0-9-]*`. The scope is not part of the pack name.
- `name` must equal the short package name (the part after the npm scope). For `@acme/render-harness-cap-example`, set `name: "render-harness-cap-example"`. The validator errors on a mismatch.
- `version` is required. Reading it from `package.json` keeps it in sync with the published version.

## PackContext

Every contribution callback receives a `PackContext`:

```ts
interface PackContext {
  config: Record<string, unknown>;
  env: (name: string) => string | undefined;
  entryName: string;
}
```

- `config` is the user-supplied `config:` block from `render-harness.yaml`. Validate it inside the pack — the harness schema only checks that it is an object.
- `env(name)` reads an environment variable. Use this instead of `process.env` directly so tests can inject a fake.
- `entryName` is the `name:` field from the user's `render-harness.yaml`. Use it to scope per-deployment state (memory namespaces, table prefixes, log fields).

## envSchema

Declare every env var the pack reads. The Blueprint emitter merges these into the bundle's effective schema, and the operator install flow uses them to seed `.env.example` placeholders.

The `envSchema` field goes inside the `definePack({ ... })` call in `src/index.ts`:

```ts title="src/index.ts"
envSchema: [
  {
    name: "EXAMPLE_API_KEY",
    required: true,
    secret: true,
    description: "API key for the Example service.",
  },
  {
    name: "EXAMPLE_BASE_URL",
    required: false,
    secret: false,
    default: "https://api.example.com",
    description: "Override the API base URL.",
  },
];
```

`EnvVarSpec` fields:

| Field | Required | Notes |
| --- | --- | --- |
| `name` | yes | `SHOUT_CASE`, max 64 chars. |
| `required` | no (default `false`) | When `true`, deploy-time UI blocks until the user fills it in. |
| `secret` | no (default `false`) | When `true`, the Blueprint emits `sync: false`; never include a `default`. |
| `description` | no | Shown to deploy-time and operator users. Keep under 280 chars. |
| `default` | no | Renders into `render.yaml` for non-secret vars only. |

## localTools

Local tools are `LocalToolHandler` values from `@render-harness/core`. Define each tool as a `const` in `src/index.ts` (or split them into `src/tools.ts` for larger packs) and return them from the `localTools(ctx)` callback:

```ts title="src/index.ts"
import { getPool, type LocalToolHandler } from "@render-harness/core";

const sendNotice: LocalToolHandler = {
  definition: {
    name: "send_notice",
    description: "Send a one-line notice to the Example service.",
    source: "pack:cap-example",
    inputSchema: {
      type: "object",
      additionalProperties: false,
      properties: {
        channel: { type: "string", minLength: 1, maxLength: 64 },
        text: { type: "string", minLength: 1, maxLength: 2_000 },
      },
      required: ["channel", "text"],
    },
  },
  async handler({ input, signal, logger }) {
    const args = (input ?? {}) as { channel?: string; text?: string };
    if (!args.channel || !args.text) {
      return { content: "send_notice: channel and text are required", isError: true };
    }
    // ... do work ...
    return { content: `posted to ${args.channel}` };
  },
};
```

Handler arguments and return shape:

- `input` is whatever the model produced for the call. It is `unknown`; cast it after the runtime schema check.
- `signal` is an `AbortSignal` that fires on cancellation. Forward it to `fetch` and any cancellable IO.
- `logger` is a per-run `pino` logger with `runId`/`agentName` fields already bound.
- Return `{ content, isError? }`. `content` is the string the model sees. Set `isError: true` for tool-level failures; the loop logs and records the failure but the run continues.

### Tool namespacing

When the harness merges pack tools into an agent, every tool name is namespaced as `<pack>__<tool>`. The transformation is:

1. The npm scope is stripped from the pack name.
2. The short tool name has every `.` replaced with `_`.

Examples:

| Package | `definition.name` | Namespaced name |
| --- | --- | --- |
| `@render-harness/cap-memory-pg` | `memory.write` | `cap-memory-pg__memory_write` |
| `@render-harness/cap-github` | `github.get_issue` | `cap-github__github_get_issue` |
| `@acme/render-harness-cap-example` | `send_notice` | `render-harness-cap-example__send_notice` |

The namespaced form is what users put in `permissions.allowedTools`, `permissions.deniedTools`, and `permissions.requireApproval`. Pick stable short names — renaming a tool is a breaking change because manifests reference it by string.

Document the namespaced names in your pack's README and mention them in the agent prompts that ship with your pack.

## mcpServers

Return `McpServerConfig` values from `@render-harness/core`. The loop attaches them to every agent in the bundle. The callback goes inside `definePack({ ... })` in `src/index.ts`:

```ts title="src/index.ts"
mcpServers(ctx: PackContext): McpServerConfig[] {
  const apiKey = ctx.env("EXAMPLE_API_KEY");
  if (!apiKey) return [];
  return [
    {
      name: "example",
      transport: "http",
      url: "https://example.com/mcp",
      headers: { Authorization: `Bearer ${apiKey}` },
      allowTools: ["example.list", "example.read"],
    },
  ];
}
```

Both `transport: "stdio"` (with `command` / `args` / `env`) and `transport: "http"` (with `url` / `headers`) are supported. MCP server names are namespaced the same way tool names are (`<pack>__<server>`), and `allowTools` filters which MCP-exposed tools become visible to the model.

Returning `[]` when an env var is missing is the idiomatic way to skip an MCP server gracefully; do not throw at boot.

## skills

Skills are surfaced in the system prompt's "skills index" and loaded on demand by the built-in `load_skill` tool.

Skill bodies live as Markdown files alongside the package, typically in `skills/`. Reference them from `src/index.ts` using `import.meta.url` so the path resolves correctly whether the pack runs from source or from `dist/`:

```ts title="src/index.ts"
import { dirname, join } from "node:path";
import { fileURLToPath } from "node:url";
import type { SkillMetadata } from "@render-harness/core";

const HERE = dirname(fileURLToPath(import.meta.url));
const SKILLS_DIR = join(HERE, "..", "skills");

skills(_ctx: PackContext): SkillMetadata[] {
  return [
    {
      name: "example-runbook",
      description: "Operational runbook for the Example service.",
      whenToUse: "When the user asks about Example outages, retries, or quotas.",
      contentPath: join(SKILLS_DIR, "example-runbook.md"),
    },
  ];
}
```

`contentPath` must point at a file inside the published tarball. Add `"skills"` to `files` in `package.json` so the folder is shipped to npm, and write each skill body as a Markdown file under `skills/`:

```md title="skills/example-runbook.md"
# Example service runbook

Use this skill when the Example service returns 429 or 5xx errors.

1. Check `/status` endpoint at https://example.com/status.
2. Back off with jitter; the default retry budget is 3.
3. If quota is exhausted, surface the error to the user and stop.
```

## connectors

Connectors mount inbound HTTP receivers on the web service at `/connectors/<key>`. They verify provider auth, normalize the event, enqueue work onto the worker, and return quickly. Connector packs need a `runtime-worker`-shaped bundle to receive and execute the enqueued runs.

Add the callback in `src/index.ts`. For non-trivial verification logic, split it into `src/verify.ts` and `src/extract.ts` (see `@render-harness/cap-webhook-generic` for the canonical layout):

```ts title="src/index.ts"
import {
  type ConnectorContribution,
  type ConnectorWebCtx,
  type PackContext,
} from "@render-harness/registry";

connectors(ctx: PackContext): ConnectorContribution[] {
  return [
    {
      key: "example",
      async webhook(req, webCtx): Promise<Response> {
        const body = await req.text();
        // verify signature here ...
        const agent = webCtx.resolveAgent(/* optional configured agent name */);
        const result = await webCtx.enqueueRun({
          agentName: agent.name,
          agentVersion: agent.version,
          userId: "cap-example",
          initialContent: [{ type: "text", text: body }],
          metadata: { connector: "example" },
        });
        return Response.json(result, {
          status: result.status === "enqueued" ? 202 : 200,
        });
      },
    },
  ];
}
```

`ConnectorWebCtx` exposes:

- `pool` — the shared Postgres pool.
- `logger` — a connector-scoped logger.
- `config` — the same user config the pack received.
- `resolveAgent(name?)` — returns the configured target agent (or the first agent in the bundle) and throws a clear error if none match.
- `enqueueRun(args)` — fire-and-forget run for one-shot deliveries.
- `enqueueIntoConversation(args)` — multi-turn delivery; reuses the existing conversation and skips if a turn is already active.

Connector key rules:

- `key` must match `[a-z0-9][a-z0-9-]*`.
- Reserved keys are rejected: `agents`, `blueprint`, `config`, `connectors`, `conversations`, `deployment`, `diagnostics`, `healthz`, `runs`, `schedules`, `ui`, `usage`.
- Keys must be unique across all packs installed in the bundle. The catalog validator checks for collisions across first-party packs.

Most production connector packs expose an `accessMode` config knob (`read` vs `read_write`) and conditionally register write tools in `localTools`. See `@render-harness/cap-github` for the canonical pattern.

## renderServices

Use `renderServices` when a pack needs its own Render service to function — typically a private service sidecar that the agent's tools dial into. The hook runs at build time only; the runtime library never calls it.

Add the callback in `src/index.ts`. If the sidecar ships from your pack's repo, also commit the sidecar source (for example `sidecar/Dockerfile` and `sidecar/src/server.ts`) and reference the Dockerfile path relative to the user's harness repo root:

```ts title="src/index.ts"
import type { RenderServiceSpec } from "@render-harness/registry";

renderServices(ctx: PackContext): RenderServiceSpec[] {
  return [
    {
      type: "pserv",
      name: `${ctx.entryName}-example-sidecar`,
      runtime: "docker",
      dockerfilePath: "./Dockerfile.sidecar",
      plan: "starter",
      envVars: [
        { key: "EXAMPLE_API_KEY", sync: false },
        {
          key: "DATABASE_URL",
          fromDatabase: { name: `${ctx.entryName}-pg`, property: "connectionString" },
        },
      ],
    },
  ];
}
```

`RenderServiceSpec` is intentionally a narrow subset of the Render Blueprint schema: `type` is `pserv` or `worker`, `runtime` is `node` or `docker`, and `envVars` accepts literal values, `sync: false` placeholders, `fromService`, `fromDatabase`, and `fromGroup`. After updating the manifest, the user runs `pnpm build:bp` to regenerate `render.yaml`; the pack's services land in the same file.

## migrations

If your pack needs its own Postgres tables (for example a long-term memory store, a polling cursor table, or any pack-owned state), declare them via the `migrations` slot. The harness applies them at boot, in order, before any agent code runs.

```ts title="src/index.ts"
import type { MigrationFile } from "@render-harness/registry";

const SEEN_NOTES_SQL = `
  CREATE TABLE IF NOT EXISTS my_pack_seen_notes (
    note_id text PRIMARY KEY,
    first_seen_at timestamptz NOT NULL DEFAULT now()
  );
`;

migrations(_ctx: PackContext): MigrationFile[] {
  return [
    { id: "0001_seen_notes", sql: SEEN_NOTES_SQL },
    // Add more entries here as the pack evolves. The id ordering
    // controls apply order within this pack.
  ];
}
```

How the runner behaves:

- The runtime adapter calls `applyMigrations(pool, { packMigrations: agent.packMigrations ?? [] })` at boot. Core migrations run first; pack migrations follow, under the same advisory lock so concurrent boots of web + worker + cron don't collide.
- Each migration runs in its own transaction. On success the runner writes `(packName, id)` to the `agent_pack_migrations` tracking table. On the next boot, already-applied entries are skipped — there's no cost to leaving every migration in the array.
- A failing migration aborts boot with an actionable error naming the pack and migration id. The transaction is rolled back, so the database isn't left half-migrated. Fix the SQL in your pack and redeploy.
- The same `(packName, id)` contributed by multiple agents in a bundle is deduped — the runner applies it once.

Conventions worth following:

- **Make every migration idempotent on its own** (`CREATE TABLE IF NOT EXISTS`, `CREATE EXTENSION IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`). The tracking table is belt-and-suspenders, not your only safeguard — and during development you may need to re-run a migration manually against a real DB without the tracking step.
- **Prefix all table names with your pack's identifier** (`memory_pg_*`, `cap_granola_*`) so two packs can't collide on shared globals. The harness owns the `agent_*` prefix.
- **Treat already-released migration ids as immutable.** If you need to change behavior, add a new migration (`0002_*`) that ALTERs the existing table — never edit the old SQL in place. Editing already-applied SQL is a silent bug because the runner sees the id in `agent_pack_migrations` and skips the new content.
- **Don't put data backfills in `migrations`.** They run on every harness boot for new deployments and block startup. If you need a backfill, ship it as a separate one-shot script or a tool the operator can call from the UI.

The runner is the right place for **schema work the pack owns**. For schema work the user owns (custom application tables, business data), continue using your own migration tooling.

## Stateful packs and lazy bootstrap

Tool handlers can pull the shared Postgres pool and logger directly from core. Import them at the top of `src/index.ts`:

```ts title="src/index.ts"
import { getPool, getLogger } from "@render-harness/core";
```

When a pack needs its own schema, bootstrap it lazily on first call rather than at module load. The canonical pattern (from `@render-harness/cap-memory-pg`) lives at the top level of `src/index.ts`:

```ts title="src/index.ts"
let bootstrapped = false;
async function ensureSchema(): Promise<void> {
  if (bootstrapped) return;
  await getPool().query(`
    CREATE TABLE IF NOT EXISTS cap_example_state (
      id BIGSERIAL PRIMARY KEY,
      namespace TEXT NOT NULL,
      key TEXT NOT NULL,
      value TEXT NOT NULL,
      UNIQUE (namespace, key)
    );
  `);
  bootstrapped = true;
}
```

Call `await ensureSchema()` at the top of every tool handler that touches the table.

Lazy bootstrap keeps cold start fast for agents that never invoke the pack, and avoids forcing migration ordering on the host repo.

Module-level state (like `bootstrapped`) is one of the reasons capability packs are bundle-wide rather than per-agent: each pack instance is shared across every agent that runs in the same process.

## Validate

Before publishing, build and validate the package. Run these from the pack's package root (the directory containing `package.json`):

```sh
pnpm build
pnpm exec render-harness-capability validate .
```

The validator checks:

- `package.json` shape: name, version, ESM type, `render-harness-cap` keyword, ESM exports, `repository`, gallery metadata.
- The default export imports cleanly and parses as a `CapabilityPack`.
- `pack.name` matches the package's short name.
- Connector contributions can only be validated structurally without invoking the factory; if the pack has connectors, write integration tests that exercise the webhook with a synthetic request.

Add `--json` to get machine-readable output for CI.

For workspace authors, the same binary can validate the official capability catalog (`capability-catalog/index.yaml` at the harness repo root) and cross-check first-party packs in one shot. Run from the harness repo root:

```sh
pnpm exec render-harness-capability catalog validate \
  capability-catalog/index.yaml \
  --workspace-root .
```

## Test

A capability pack benefits from three test layers. Tests live next to source as `src/*.test.ts` and run through Vitest:

1. **Unit tests** for tool input parsing, signature verification, and config defaults (`src/index.test.ts`, `src/verify.test.ts`).
2. **Integration tests** that stand up Postgres and Key Value via `pnpm db:up`, register the pack against a real agent definition, and assert the namespaced tool names show up (`src/integration.test.ts`).
3. **Snapshot tests** for any generated Render service blocks (`src/render-services.test.ts`).

Vitest with `--passWithNoTests` is the workspace default. Add a minimal `vitest.config.ts` at the package root if you need to customize:

```ts title="vitest.config.ts"
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "node",
    include: ["src/**/*.test.ts"],
  },
});
```

For connector packs, use `Request` and `Response` from the global fetch API to drive the webhook handler directly without standing up an HTTP server.

## Publish to npm

Publish through your normal release flow. For first-party packs in this repo, that means a Changeset:

```sh
pnpm changeset
# pick a `patch` bump for the cap pack
pnpm release
```

Capability packs are versioned independently of `@render-harness/core` and friends. Bump them only when the capability itself changes. See [Harness versioning](/harness-versioning/) for the full policy, and `AGENTS.md` in the repo root for the realignment cookbook if a pack drifts off the family line.

For external packs:

- Confirm the package name is unique on npm and the scope is one you control.
- Set up [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers) so your release workflow uses OIDC instead of long-lived `NPM_TOKEN`. The `repository.url` field is mandatory for provenance attestation.
- Tag the GitHub release so consumers can pin to a specific version.

## Register in a catalog

The npm keyword `render-harness-cap` makes the package discoverable, but the operator UI's capability gallery reads from a curated catalog. To list an official pack, append an entry to `capability-catalog/index.yaml` at the harness repo root:

```yaml title="capability-catalog/index.yaml"
- package: "@acme/render-harness-cap-example"
  name: Example
  description: One-line description of what the pack adds.
  categories: [tools]
  provider: Example
  repo: https://github.com/<owner>/<repo>
  docs: https://github.com/<owner>/<repo>#readme
  license: MIT
  maintainer: <owner>
  versionRange: "^0.1"
  requiresHarness: "^0.2"
  features: [tools]                # any of: tools, connectors, skills, services
  envVars:
    - name: EXAMPLE_API_KEY
      required: true
      secret: true
      description: API key for the Example service.
  permissions:
    accessMode: read                # read | read_write | mixed
    network: true
    filesystem: none
    sidecarServices: false
  connectors: []                    # for connector packs only

    testCommand: pnpm --filter @acme/render-harness-cap-example test

Bumping `versionRange` in this file documents the supported range but does not change scaffolder output; that comes from running `pnpm tsx scripts/bundle-gallery.ts` in `packages/create-render-agent` (see `AGENTS.md`).

## How users consume your pack

Once published, users add the package as a dependency in their harness repo:

```sh
pnpm add @acme/render-harness-cap-example
```

And reference it in their `render-harness.yaml`:

```yaml title="render-harness.yaml"
capabilities:
  - pack: "@acme/render-harness-cap-example"
    config:
      defaultChannel: alerts
```

Their `pnpm build:bp` step:

1. Resolves the pack from `node_modules`.
2. Calls every contribution callback with their `config` and `env`.
3. Merges `envSchema` into the bundle's effective schema and emits `render.yaml` env vars.
4. Calls `renderServices()` and inlines the result into `render.yaml`.

At runtime, the worker (or web / cron / workflows) loads the same pack, calls `localTools`, `mcpServers`, `skills`, and `connectors`, and namespaces every contributed name as described above.

Already-deployed harnesses install packs through the operator UI, which commits the manifest and `package.json` changes through the wizard service and the GitHub App. See [Capabilities](/capabilities/#installing-after-deployment) for the post-install steps.

## Permissions and approval

Users gate pack tools through `permissions` on the bundle or per agent in their `render-harness.yaml`:

```yaml title="render-harness.yaml"
agents:
  - id: chat
    # ...
    permissions:
      allowedTools:
        - cap-example__send_notice
      requireApproval:
        - cap-example__send_notice
```

When you ship a pack that mutates external state (writes to an API, posts a Slack message, opens a PR), call it out in the README and recommend `requireApproval` in the example config. Packs that branch tool surface on user config — for example, only registering write tools when the user sets `accessMode: read_write` — should document the trigger explicitly. The `@render-harness/cap-github`, `@render-harness/cap-linear`, and `@render-harness/cap-slack` packs all use this pattern.

## Checklist

Before submitting a pack:

- `package.json` has `"type": "module"`, the `render-harness-cap` keyword, `exports["./package.json"]`, and `repository.url`.
- `definePack` `name` matches the package short name.
- Every contribution callback handles missing env gracefully (return `[]` rather than throwing).
- `envSchema` lists every env var the pack reads.
- Local tools use stable namespaced names and document them in the README.
- Connectors choose a non-reserved, lower-case `key` that won't collide with other packs.
- `pnpm exec render-harness-capability validate .` passes with no errors.
- A short README explains config, the namespaced tool names, required env vars, and whether tools mutate state.
- Test command listed in the catalog `quality.testCommand` actually runs cleanly.
